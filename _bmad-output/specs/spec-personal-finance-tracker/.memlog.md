- (direction) Input: polished product brief (brief-bmad-personal-finance-tracker-2026-07-24). Rich structured upstream artifact; distilled directly, no elicitation.
- (decision) Why = vision-to-realize (canonical BMad-method demo, primary) + pain-to-solve (family wants private, shared income/spending tracking, secondary).
- (capability) CAP-1: Log a transaction as an 'in' (income) or 'out' (spending) with amount, date, and purpose/category. Success: entry persists and appears in that user's history with correct type/amount/date/category.
- (capability) CAP-2: Classify transactions with categories (the 'purpose'). Success: a user assigns a category on entry and transactions are grouped by it in lists and charts.
- (capability) CAP-3: Review transaction history via a list with basic filtering. Success: user lists their transactions and filters (e.g. by type/category/date) to a correct subset.
- (capability) CAP-4: See income/spending broken down by category and over time via charts. Success: dashboard renders a by-category and an over-time chart matching the underlying transactions.
- (capability) CAP-5: Per-user access via static login; each family member has their own view. Success: after logging in with static credentials, a user sees the correct scoped data and cannot act as another user.
- (constraint) Self-hosted single instance on family's own hardware; data stays private, no third-party cloud.
- (constraint) Server-rendered, mobile-friendly UI optimized for quick phone entry (bends toward server-side rendering over SPA).
- (constraint) Demo-grade auth only: static, hard-coded usernames/passwords — rules out registration, password reset, production authN/authZ.
- (constraint) Scope stays small and traceable (BMad demo); every feature must trace back to the brief — bends against gold-plating.
- (constraint) Tech stack fixed: Quarkus (Java) + Qute templating + relational DB (see stack.md companion).
- (note) Non-goals: real/production auth; bank connections & CSV/API import; budgets/limits/alerts/goals; multi-currency; native mobile apps; shared/joint accounts & complex household roles.
- (note) Success signal: a family member logs a purchase on their phone in a few taps, dashboard immediately shows the month's spending by category; and the whole path brief->running feature is traceable as a BMad worked example.
- (assumption) Family status quo today is spreadsheets or nothing (from brief [ASSUMPTION]).
- (assumption) Family size ~2-5 users (from brief [ASSUMPTION]).
- (assumption) Persistence to a relational DB, likely Postgres via Hibernate/Panache (from brief [ASSUMPTION]); H2/SQLite may be simpler for self-hosting.
- (assumption) Single currency for v1 (from brief [ASSUMPTION]).
- (question) Data visibility: does each user see only their OWN transactions, or a shared HOUSEHOLD view? Brief says both 'their own view' and 'where OUR money went' — load-bearing for CAP-4/CAP-5, needs a human decision.
- (question) Which database for v1 — Postgres, or H2/SQLite for zero-dependency self-hosting?
- (question) Which single currency (and display format), and is it configurable per instance?
- (question) How many static users and who defines the credential set (config file vs compiled-in)?
- (question) Are categories a fixed predefined list, or user-managed (create/edit/delete)?
- (decision) Companion stack.md (spec-authored) holds the fixed tech stack: Quarkus, Qute, relational DB, server-rendered mobile-friendly UI.
